# 공통 운영 규칙

## 요구사항과 범위

- 현재 전달된 요구사항을 기준으로 구현하고 검증합니다. 요구사항에 이미 정해진 계약을 임의로 바꾸지 않습니다.
- 순차 과제는 현재 결과를 확정한 뒤 다음 명세를 엽니다. 다음 명세를 연 뒤 이전 결과를 변경하지 않습니다.
- 애매한 부분은 팀 내부에서 근거를 확인하고 판단 이유를 room에 남깁니다. 미리 주어지지 않은 기능은 추가하지 않습니다.
- 공식 검사와 명세를 수정하거나, 검사 입력에만 맞춘 구현으로 성공을 만들지 않습니다.

## 배정과 인수인계

- 팀 단위 작업 상태는 Band Room tasks를 기준으로 합니다. 한 작업의 주 담당자와 완료 조건을 명확히 합니다.
- 개인 Agent tasks의 완료와 공유 작업의 완료를 구분합니다.
- 수신자가 room에 참여했는지 확인하고 실제 `@handle`로 직접 전달합니다.
- 인수인계에는 전체 작업 설명과 해당 요구사항 전문, 저장소 절대경로, 변경 범위, 완료 조건을 포함합니다. 링크나 메시지 ID만 전달하지 않습니다.
- 긴 요구사항은 번호가 있는 여러 직접 메시지로 나눠 전달합니다.
- 구현 완료는 검증 요청입니다. 최종 완료는 통합된 동일 커밋에 대한 독립 검증 결과를 확인한 뒤 판단합니다.

## 파일·Git·통합

- 배정받은 파일·모듈만 수정합니다. 경계 밖 변경이 필요하면 담당자와 Coordinator에게 먼저 알립니다.
- 병렬 개발은 분리된 worktree/작업 디렉터리를 사용하거나 수정·커밋 순서를 직렬화합니다. 같은 checkout에서 동시에 브랜치를 바꾸거나 stage/commit하지 않습니다.
- 시작 전에 기존 변경을 확인합니다. 다른 작업자의 미커밋 변경을 지우거나 덮어쓰지 않습니다.
- 각 결과에 전체 커밋 SHA를 남깁니다. 인수인계 후 수정되면 새 SHA로 재검증을 요청합니다.
- 통합 담당자는 작성자 이력을 보존합니다. 제출 증거가 되는 커밋을 amend, rebase, squash하지 않습니다.
- 공용 실행 설정과 의존성 파일도 작업별 수정 담당자를 한 명 정합니다.

## 검증과 실패 처리

- Reviewer는 코드와 요구사항을 검토하고, QA는 실제 동작을 실행해 확인합니다. 둘 다 원문 요구사항에 접근해야 합니다.
- 무거운 공식 컨테이너 검사는 한 번에 하나만 실행합니다. 사용 포트와 프로세스·컨테이너 소유자를 기록합니다.
- 실패 로그를 보존하고 매 실행은 새로운 출력 경로를 사용합니다.
- 코드 결함, 환경 장애, 권한 부족을 구분합니다. 실행하지 못한 검사를 통과했다고 보고하지 않습니다.
- 실패는 기대 결과·실제 결과·재현 명령·대상 SHA와 함께 원래 구현 담당자에게 전달합니다.
- 같은 실패를 원인 변화 없이 반복하지 않습니다. 새 가설이나 증거가 없으면 차단 상태와 다음에 필요한 조건을 보고합니다.
- 정리할 때는 자신이 만든 리소스만 종료·삭제합니다.

## 메모리와 권한

- 결정·실패 경험을 저장할 때 원문 위치, 관련 커밋, 확인 상태를 함께 남깁니다. 코드 변경 후 과거 검증을 현재 결과로 재사용하지 않습니다.
- 아직 열지 않은 명세, 자격증명, 개인정보를 공유 메모리에 넣지 않습니다.
- room과 Git 기록이 재현 근거입니다. 공유 메모리는 그 기록을 찾는 보조 수단으로 사용합니다.
- 주어진 권한 경계를 지킵니다. 연습에서는 필요한 환경 승인을 요청할 수 있습니다.
- 제출용 무인 실행에서는 시작 전에 필요한 권한을 검증합니다. 실행 중 추가 승인이 필요하면 우회하지 말고 차단 원인과 증거를 보고합니다.
